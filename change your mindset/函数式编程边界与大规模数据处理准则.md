# 函数式编程边界与大规模数据处理准则

## 1. Traverse / Sequence 的规模红线

在 LanguageExt 中，`Traverse` 与 `Sequence` 通过 `Apply`（`<*>`）逐层嵌套组合 effect。**集合规模超过约 100 个元素时，即有栈风险；超过 1000 个时，几乎必爆。**

8000 个文件的典型死亡代码：

```csharp
static Eff<RT, Seq<HashedSlide>> HashSlides(Seq<string> files) =>
    files.Traverse(HashSlide).As();   // StackOverflowException，不可捕获
```

根因：解包时形成数千层深的调用链，超出 C# 默认线程栈（~1MB）。C# 没有可靠尾递归优化（TCO），LanguageExt 也未对大集合做蹦床保护。

| 规模 | 方案 | 理由 |
|------|------|------|
| < 100 元素 | `Traverse` / `Sequence` | 调用链浅，类型安全，表达力强 |
| 100 ~ 1000 元素 | `Fold` + `Bind`（需压测） | 深度可控，但仍受栈限制 |
| > 1000 元素 / 规模未知 | 命令式循环包在 `Eff.lift` 内 | 栈安全、可异常隔离、可并行 |

## 2. 正确写法：命令式循环裹一层 Eff

```csharp
public static Eff<RT, SlideGroupedByMD5> ProcessFolder(string path) =>
    from files in Directory<RT>.enumerateFiles(path, "*.ppt?", SearchOption.AllDirectories)
    from result in Eff<RT>.lift(() =>
    {
        var acc = HashMap<string, Seq<string>>();
        foreach (var file in files)
        {
            try
            {
                using var fs = File.OpenRead(file);
                var md5 = Convert.ToHexString(MD5.HashData(fs)).ToLowerInvariant();
                acc = acc.AddOrUpdate(md5,
                    Some: exist => exist.Add(file),
                    None: () => Seq(file));
            }
            catch
            {
                // 异常隔离：单个文件失败不阻断整体流程
            }
        }
        return new SlideGroupedByMD5(acc);
    })
    select result;
```

对外仍是纯函数式接口，对内用 `foreach` 避开深度 monadic 嵌套。若磁盘 IO 是瓶颈，内部可替换为 `Parallel.ForEach` + 线程安全字典，再最终转回 `HashMap`。

## 3. FP 在 C# 中的真实能力边界

函数式编程**用途不窄**，以下场景非常适合：

- 业务规则编排与验证链
- 小型工作流的状态组合
- 错误处理（`Option` / `Either` / `Eff`）
- 小型集合（<100）的声明式转换

**不适合的场景：**

- 大规模数据吞吐（>1000 元素的单条 monadic 管道）
- 需要极致性能的热点路径（delegate 分配和 trampoline 开销显著）
- 深层递归算法（C# TCO 不可靠）

---

## 4. 混合范式最佳实践

> **外层用 FP 描述"做什么"，内层大数据处理用命令式循环解决"怎么做"。**

FP 的价值在**组合**和**类型约束**，不在**替代底层循环**。在 .NET 上最务实的做法是：

1. 入口用 `Eff` / `IO` 描述副作用边界
2. 中等规模集合用 `Map` / `Bind` / `from ... select` 组合
3. 大规模集合直接落回 `foreach` / `Parallel.ForEach`
4. 纯计算（分组、过滤、聚合）保持为裸函数，不包进 `IO.lift`

---

## 5. 一句话总结

**超过 ~100 个元素时，禁止用 `Traverse` / `Sequence` 深度组合 effect；改用命令式循环包裹在单一 `Eff` / `IO` 中。**

## 附录：Traverse 的"嵌套组合"到底是什么

### 先说结论

不是"执行 8000 个操作"，而是"把 8000 个操作**塞成了一个俄罗斯套娃**，拆开套娃的时候栈炸了"。

### 用 3 个文件演示

`Traverse` 内部实现（简化）：

```csharp
Seq("a.ppt", "b.ppt", "c.ppt").Traverse(HashSlide)

// 等价于逐层 Apply 拼装：
Pure(Seq.Empty)
  .Apply(HashSlide("a.ppt"))   // 不执行，只拼装
  .Apply(HashSlide("b.ppt"))   // 不执行，只拼装
  .Apply(HashSlide("c.ppt"))   // 不执行，只拼装
```

**关键：`Apply` 不做实际工作，它只是"拼装说明书"**。运行前得到的 Eff 对象结构如下：

```
Eff(
  内部 = Apply(
    左边 = Apply(
      左边 = Apply(
        左边 = Pure([]),
        右边 = Eff(计算a.ppt的MD5)
      ),
      右边 = Eff(计算b.ppt的MD5)
    ),
    右边 = Eff(计算c.ppt的MD5)
  )
)
```

### 运行时拆套娃

等你最后调用 `.Run()`，LanguageExt 开始一层一层剥开：

```
Run(最外层Eff)
  → 拆开发现是 Apply(A, B)
    → 先 Run(A)
      → 拆开发现又是 Apply(C, D)
        → 先 Run(C)
          → 拆开发现又是 Apply(E, F)
            → 先 Run(E)
              → Run(Pure)    ← 终于到最底层
            → 再 Run(F)
          → 再 Run(D)
        → 再 Run(B)
    → 组合结果
```

**本质：不是平铺的"算完 A 算 B 算 C"，而是"为了算 C，必须先拆开 B；为了算 B，必须先拆开 A"**。

3 个文件时，调用链只有几层深，没事。  
8000 个文件时，拆套娃需要 **8000 层深度的函数调用栈**，C# 默认 1MB 线程栈直接爆炸。

### 对比一下循环

```csharp
// 循环是平铺的，调用栈永远只有 1 层深
foreach (var file in files)
{
    var md5 = Hash(file);  // 调用返回后栈帧立即释放
}
```

| 方式 | 调用栈深度 | 8000 元素安全性 |
|------|-----------|----------------|
| `foreach` 循环 | O(1)，固定 1 层 | 安全 |
| `Traverse` + `Apply` | O(N)，与元素数成正比 | 爆栈 |

### 一句话

`Traverse` 把 `Eff` 像巧克力球一样一层一层包了起来。8000 层巧克力球，吃的时候（`Run`）要一层一层剥，剥到一半手（栈）就断了。
